我看完当前仓库后，建议是：**不要继续往 DAP / native host / engine attach 方向堆功能了，先做一轮核心重构。**

现在代码已经验证了很多东西：有 Parser、Graph C# subset analyzer、BindingRegistry 雏形、Behavior IR、蓝图投影、debug emit、DebugMap、probe、JSON-RPC server、DAP/native host 验证路径。问题不是“做不出来”，而是**核心编译链还没稳定，调试/宿主集成已经抢跑**。这会让后面的蓝图回写、`.ashlayout`、稳定资产 ID、VkEngine 回接越来越脆。

## 当前仓库的状态判断

当前 solution 里有四个项目：`ScriptLab`、`ScriptLab.Tests`、`ScriptLab.ScriptAssets`、`ScriptLab.Analyzers`。 主项目现在是一个 `net10.0` 的 Exe，并且直接引用 Roslyn；它同时排除了 tests、script assets、analyzers、samples 的编译项。 Analyzer 项目则通过 link 的方式复用 `Shared/GraphCSharpRuleSet.cs`、`GraphCSharpBindingRegistry.cs`、`GraphCSharpRestrictionAnalyzer.cs`。

这说明当前结构还是 **实验型单体**，不是长期包结构。它和原计划里“独立 ScriptLab 原型拆成 Abstractions / Compiler / Runtime / Tests”的方向还没对齐。

功能上，当前已经明显超过 Phase 1/2：`BehaviorIr.cs` 里同时定义 IR model、lowerer、IR text reporter、verifier/runtime-like executor；`BlueprintGraph.cs` 已经能从 IR 投影节点和边；`DebugScriptCompiler.EmitFile` 已经能 lower、project、生成 probe manifest、插桩、emit DLL/PDB、写 DebugMap。

但从架构成熟度看，**核心语义层还偏薄，调试层偏厚**。`ScriptLabServer.LoadGraph` 现在不仅 lower/project，还会 emit debug assembly、创建 DebugSession、加载 DebugScriptHost、创建 breakpoint backend。也就是说，“加载图”已经带上了编译调试产物和 runtime host 副作用。 这对技术验证没问题，但对编辑器和引擎集成会变成隐患。

## 最需要优先改的地方

### 1. 先拆项目边界，不要继续让 `ScriptLab` 变大

我建议把当前单体拆成这样：

```text
src/
  Asharia.GraphCSharp.Abstractions/
    ids, diagnostics, attributes, public data contracts
    不依赖 Roslyn

  Asharia.GraphCSharp.Compiler/
    parse
    subset analyzer
    semantic binding
    type/effect/context check
    IR lowering
    blueprint projection
    source rewrite
    依赖 Roslyn + Abstractions

  Asharia.GraphCSharp.Analyzers/
    Roslyn DiagnosticAnalyzer
    只包装 Compiler 的规则/诊断

  Asharia.GraphCSharp.Runtime/
    BehaviorProgram
    Interpreter
    ProgramCache
    ScriptInstance table
    EventQueue
    MutationQueue
    runtime diagnostics
    不依赖 Roslyn

  Asharia.GraphCSharp.Debug/
    SourceMap / DebugMap
    DebugProbe manifest
    breakpoint resolver
    source-instrumented debug backend
    future IR-to-C# backend

  Asharia.ScriptLab.Server/
    JSON-RPC orchestration

    parse / dump-ir / dump-graph / verify-ir / emit-debug / server
```


当前 `Program.cs` 已经有很多命令分支，包括 `dump-ir`、`dump-graph`、`emit-debug`、`inspect-debug`、`break-debug`、`run-debug`、`debug-smoke`、`server`、`validate-host`、`verify-ir` 等。 这部分应该保留 CLI 行为，但把每个命令背后的逻辑挪进服务类，避免 `Program.cs` 继续膨胀。

### 2. BindingRegistry 必须从字符串表升级成稳定 ID schema

这是当前最大技术债。

现在的 `GraphCSharpFunctionBinding` 只有两个字段：`CSharpName` 和 `FunctionId`；注册表里硬编码了 `Input.KeyDown`、`Transform.Translate`、`GraphDebug.Inspect`、`GraphDebug.Watch`。 调用绑定也是用 `memberAccess.ToString()` 或 `invocation.Expression.ToString()` 做字符串匹配。

这对 demo 可以，但不能作为资产系统。原方案要求 Graph C# 不把 C# 符号名作为长期资产身份，而是绑定到稳定 `FieldId` / `FunctionId`。 当前 IR 的字段还是 `BehaviorIrField(string Name, string Type, string? InitialValue)`，`LoadField` 也存 `FieldName`，不是 `FieldId`。  Debug host 的 `GetFieldId` 也直接返回 `field.Name`。

建议下一步引入这些核心类型：

```csharp
public readonly record struct TypeId(string Value);
public readonly record struct FieldId(int Value);
public readonly record struct FunctionId(string Value);

public sealed record BoundField(
    TypeId OwnerTypeId,
    FieldId FieldId,
    string CSharpName,
    GraphType Type,
    FieldPersistence Persistence,
    FieldEditorMetadata Editor);

public sealed record BoundFunction(
    FunctionId FunctionId,
    string CSharpQualifiedName,
    IReadOnlyList<GraphParameter> Parameters,
    GraphType? ReturnType,
    EffectFlags Effects,
    ScriptContextMask AllowedContexts,
    string DisplayName,
    string Category,
    int Version,
    FunctionId? ReplacedBy);
```

然后把 IR 改成：

```csharp
public sealed record BehaviorIrField(
    FieldId FieldId,
    string Name,
    GraphType Type,
    string? InitialValue,
    BehaviorSourceSpan Source);

public sealed record BehaviorIrLoadField(
    string Target,
    FieldId FieldId,
    BehaviorSourceSpan Source);
```

样例也要改。现在 `PlayerMove.ash.cs` 是 `public class PlayerMove`，没有 `[Behavior]`，字段也没有 `[Field(id)]`，只靠 namespace 推导 behavior id。 `PrivateSerializedField.ash.cs` 甚至是 `[Field]` 没有 id。 建议 v0 样例直接对齐规范：

```csharp
using Asharia.Behavior;

namespace com.game;

[Behavior("com.game.PlayerMove")]
public sealed partial class PlayerMove : BehaviorComponent
{
    [Field(1), Expose, Range(0f, 20f)]
    public float Speed = 4.0f;

    protected override void Update(float delta)
    {
        if (Input.KeyDown(Key.W))
        {
            Transform.Translate(Self, new Vec3(0f, 0f, Speed * delta));
        }
    }
}
```

### 3. Analyzer 要从“黑名单检查”升级为“白名单 + 语义检查”

现在 `GraphCSharpRuleSet` 已经覆盖不少禁用项，比如 lambda、await、yield、try/throw、goto、lock、unsafe、stackalloc、delegate/event、array allocation、LINQ query、for/foreach/while/do。 但它目前定义的诊断只有 `AGC0001`、`AGC0002`、`AGC0003`、`AGC0007`、`AGC0008`、`AGC0009`。

原方案里更关键的几类还没落地：

```text
AGC0004 Missing stable field id
AGC0005 Illegal context call
AGC0006 Hidden side effect
AGC0010 Source map unavailable
```

这些不能靠纯 syntax walker 做完。当前 `GraphCSharpSubsetAnalyzer` 本质是遍历 syntax node，然后调用 restriction analyzer。  下一步应该加一个 semantic pass：

```text
Syntax pass:
  只管语法白名单/黑名单

Semantic pass:
  解析符号
  绑定函数/字段
  检查 FieldId
  检查类型
  检查 effect
  检查 allowed context
  检查 source span 可映射性
```

同时建议把规则从“看到某些 SyntaxKind 就报错”的黑名单，逐步改成：

```text
GraphCSharpAllowedSyntaxMatrix
  CompilationUnit
  FileScopedNamespace / NamespaceDeclaration
  UsingDirective
  ClassDeclaration
  FieldDeclaration
  MethodDeclaration
  Block
  LocalDeclarationStatement
  ExpressionStatement
  IfStatement
  ElseClause
  ReturnStatement
  InvocationExpression
  ObjectCreationExpression for registered value structs only
  BinaryExpression allowed operators only
  LiteralExpression
  IdentifierName
  MemberAccessExpression
```

这样将来 C# 新语法出现时，不会默默通过。

### 4. `BehaviorIr.cs` 应该拆掉，而且 IR 不应该保存 unsupported node

现在 `BehaviorIr.cs` 同时承担了太多职责：IR records、lowerer、debug site 分配、文本 dump、验证执行器都在一个文件里。IR 指令里还包含 `BehaviorIrUnsupportedStatement` 和 `BehaviorIrUnsupportedExpression`。

建议拆成：

```text
Compiler/Ir/BehaviorIrModel.cs
Compiler/Ir/BehaviorIrInstruction.cs
Compiler/Lowering/BehaviorIrLowerer.cs
Compiler/Lowering/ExpressionLowerer.cs
Compiler/Lowering/StatementLowerer.cs
Compiler/DebugSites/DebugSiteAssigner.cs
Compiler/Text/BehaviorIrText.cs

Runtime/Interpreter/BehaviorInterpreter.cs
Runtime/Interpreter/BehaviorFrame.cs
Runtime/Bindings/IRuntimeFunctionRegistry.cs
Runtime/Diagnostics/RuntimeDiagnostic.cs
```

更重要的是：**合法 Graph C# lower 完之后，不应该还有 Unsupported IR 指令。**
如果不能 lower，就应该在 analyzer/binder/checker 阶段报 `AGC` 诊断，直接禁止生成 valid module。

当前 verifier 也只是验证器，不是真正 runtime。它只支持 `asharia.input.keyDown`、`asharia.transform.translate`，二元操作只支持 `Multiply`。  这适合作为测试 helper，但不适合作为 Phase 7 的 interpreter runtime。

Phase 7 应该补的是：

```text
BehaviorInterpreter
  ExecuteEvent(program, instance, eventId, args, context)
  locals / temps / fields
  runtime function dispatch
  effect validation
  diagnostics collection
  mutation queue output
```

`Transform.Translate` 不应该只记录 observed call，而应该进入：

```text
MutationQueue.Enqueue(
  new TranslateCommand(entity, offset, sourceSiteId, functionId));
```

这和原方案里“World 修改必须走 mutation queue”的边界一致。

### 5. 图节点 ID 和 debugSiteId 现在还不够稳定

当前蓝图节点 ID 是 `n0`、`n1` 这种递增 ID。`CreateGeneratedNode` 和 `CreateNode` 都用 `nextNodeId++`。 这对当前一次性投影可以，但不能作为 `.ashlayout` 的持久 key。

当前 `debugSiteId` 生成也包含：

```text
behaviorId
functionName
blockName
instructionIndex
instruction type
source file
source start
source length
formatted instruction
```



这意味着只要用户在前面插入一条语句，`instructionIndex`、source start、甚至 block 结构都可能变化，导致后面节点的 debugSiteId 跟着变。对断点和 DebugMap 这是可接受的短期方案；对 layout remap 和长期节点身份不够稳。

建议拆成两种 ID：

```text
GraphNodeId
  当前视图内 ID，可以是 n0/n1

DebugSiteId
  当前编译/调试映射 ID，服务断点/trace/watch

NodeIdentity
  布局和回写用的语义身份
```

`NodeIdentity` 可以这样设计：

```csharp
public sealed record GraphNodeIdentity(
    string FunctionName,
    string NodeKind,
    string? BoundId,             // FunctionId / FieldId / TypeId
    SourceAnchor SourceAnchor,
    int OrdinalAmongSiblings,
    string SourceTextHash);
```

`.ashlayout` 只存：

```json
{
  "schemaVersion": 1,
  "nodes": [
    {
      "identity": "...",
      "x": 120,
      "y": 340,
      "collapsed": false
    }
  ]
}
```

然后加 layout remap 测试：

```text
修改 literal，不丢布局。
修改 Key.W -> Key.S，不丢布局。
插入一条 statement，其他节点布局不丢。
重排两个 statement，节点布局跟随 statement。
删除 .ashlayout，可从 .ash.cs 重建图。
```

### 6. 当前 debug emit 很有价值，但名字上不要把它当 Phase 9 的 IR 后端

`DebugScriptCompiler.EmitFile` 当前流程是：

```text
LowerFile
Project graph
Create probe manifest
Parse original source
DebugInstrumentationRewriter rewrite original syntax tree
Compile instrumented source to DLL/PDB
Create DebugMap
```



这条链路很有价值，尤其是 `#line hidden`、probe、PDB sequence point、DebugMap 的验证。`DebugInstrumentationRewriter` 会插入 `DebugProbe.Enter(...)`，也会把 `GraphDebug.Inspect/Watch` 改成 `DebugProbe.Value(...)`。   `DebugMapFactory` 也已经把 graph node、source span、probe id、PDB sequence point、method token、IL offset、local scope 串起来了。

但这不是严格意义上的：

```text
Behavior IR -> generated C# -> DLL/PDB
```

它更准确的名字应该是：

```text
SourceInstrumentedDotnetDebugBackend
```

也就是“把原始 `.ash.cs` 插桩后编译”。真正的 Phase 9 后端应该另起：

```text
IrToCSharpBackend
  BehaviorIrModule -> canonical generated C#
  generated C# -> Roslyn Compilation.Emit
```

然后加一条非常关键的测试：

```text
Interpreter trace == SourceInstrumentedDotnetBackend trace
Interpreter trace == IrToCSharpBackend trace
```

当前测试已经验证了 emit 文件、probe、DebugMap、PDB sequence point、运行后 probe event、Watch value event。   下一步应该补的是**语义一致性**，不只是“调试事件能出来”。
